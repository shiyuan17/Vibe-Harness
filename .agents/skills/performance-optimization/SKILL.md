# 性能优化

## Overview

先测量，再优化；用同一组样本复测。目标不是少跑命令，而是减少重复证据、等待与资源争用，同时保持安全边界和验收标准。

## When to Use

- 多个会话的墙钟持续偏长且 Agent 推理不是主因；验证、构建、测试、Hook 或 worktree 生命周期存在重复执行。
- 需要决定缓存、并行、跳过或合并命令，并给出可回滚方案。
- 不适用：单一失败需要定位根因、只做功能实现，或没有可观察耗时证据。

## Process

1. 固定优化前样本：范围、会话数、命令、退出状态、单项耗时与失败率；缺样本先补观测。
2. 按墙钟贡献排序：启动、重复命令、缓存未命中、锁等待、依赖安装、测试本体；区分必然成本与重复成本。
3. 为每个候选写出收益假设、证据、影响面和回滚方式，只保留能由数据区分优先级的项。
4. 先做不改语义的工程优化（去重、显式覆盖、内容寻址缓存、分项计时），再评估跳过、并发与门禁调整。
5. 保持 fail-closed：内容、工具链、基线或收据不可证明时按 miss/blocked 处理。
6. 每次只改一个主要变量，运行对应聚焦测试；发布前后使用同一任务、代码树和环境复测。
7. 报告优化前后的命令数、总耗时、p50/p95、失败率和仍占主导的成本项；没有前后数据不宣称提升比例。

按需读取：`references/command-budget.md`（层级裁剪）、`references/cache-and-receipts.md`（缓存与证据）、`references/verification-strategy.md`（ledger 与合并树）。

## Rationalizations

- “多跑几条更保险”或“缓存可能不准，所以不用”：应消除重复的低层证据并修复缓存键与 fail-closed 校验，而不是接受已知成本。
- “Hook 慢一点更安全”：Hook 是纵深防御；硬边界与普通策略应分开。
- “删掉一条命令就是优化”：删掉唯一高层证据只是把成本转移到返工和事故。

## Red Flags

- 没有基线就给出百分比或“明显更快”的结论。
- 缓存命中没有绑定相同内容、工具链和范围。
- `--only`/`--full` 被覆盖图裁剪，或风险派生矩阵被静默去重。
- 多个 worktree 同时跑后端全量、用旧租约强行回收活跃任务，或用关闭 Hook、跳过验证掩盖重复成本。

## Verification

- 复测代表性任务，记录命令数、总墙钟、单项耗时、缓存命中与失败率。
- 证明跨路径/HEAD 命中依赖树内容；文件、未跟踪内容、基线和 allowlist 环境变化会失效。
- 证明重任务由同一仓库锁串行，且门禁调整没有降低完成收据、provenance、最终树和合并结果验证。
