# 测试反模式

这些模式会让测试看似通过，却不能证明真实行为正确。

## 1. 测 mock 行为

坏味道：断言 mock 被调用了几次，却没有验证用户可观察结果。

优先做法：断言返回值、DOM、数据库状态、文件内容或请求 payload。

## 2. 为测试污染生产代码

坏味道：新增 `resetForTest()`、`getInternalState()` 等只给测试用的方法。

优先做法：通过公共接口验证行为；必要时重构依赖注入，而不是暴露内部。

## 3. 不理解依赖就 mock

坏味道：mock 的行为与真实依赖不一致，测试只证明假世界成立。

优先做法：先读真实契约；能用轻量集成测试就少 mock。

## 4. mock 不完整

坏味道：只 mock happy path，错误、超时、空值和边界全缺。

优先做法：为每个重要失败模式写明确测试。

## 5. 集成测试事后补

坏味道：单元测试都绿，但模块组合后失败。

优先做法：对跨边界行为写少量高价值集成测试，覆盖真实数据流。

## 判断问题

问自己：

- 这个测试失败时，用户能感知到什么坏行为？
- 如果实现完全错了，但 mock 仍按预期返回，测试会不会通过？
- 测试是否依赖内部步骤，而不是最终行为？
- mock 是否比真实依赖还复杂？

## 红旗

- 测试名描述实现步骤。
- 每个断言都是 `toHaveBeenCalled...`。
- 生产代码出现 test-only API。
- 改实现细节导致大量无行为变化的测试失败。
- mock 数据和真实契约无人核对。
