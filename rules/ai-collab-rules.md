# AI 协作规则

AI 协作规则把事实、决策、实现、验证和批准分开，避免模型信心被误当成项目真值。

## 指令优先级

- 平台系统指令和用户本轮明确指令优先。
- 目标项目已有且明确的本地规则优先于 Cognis 默认规则；目录级规则只作用于其子树。
- 同一层级规则冲突时停止并请求确认，不自行判断哪条“更严格”。
- 历史 memory、摘要和推断不得覆盖当前仓库事实。

## 证据边界

- 仓库文件、当前命令输出、外部契约和明确的人类决策才是证据；模型记忆和生成摘要在核对前只是待验证假设。
- 不得编造 API、字段、权限、schema、测试结果、部署结果或 reviewer 批准。
- 工具失败、读取不完整、索引过期和未验证的外部状态必须说明，并写清采用的替代方式。
- 保护用户改动；归属不清且可能重叠时，先停止再确认。

## 信息呈现

复杂请求、进度、比较、证据或交付信息按内容选择最小的可扫读结构；简单回答保持简洁，不强行套用完整模板。

### 输入整理

- 任务包含多个目标、范围、约束或验收条件时，先用紧凑结构整理为目标、范围、约束、验收标准、待决策项；这只是任务确认，不重复粘贴用户原文。
- 用户明确指定格式时优先服从用户格式；代码、路径、命令、日志、JSON 和其他原始字面量必须保持准确，不得为了排版改写。

### 输出组件

| 信息形态 | 首选结构 | 使用边界 |
| --- | --- | --- |
| 可跟踪步骤或未完成事项 | `- [ ]` / `- [x]` todo | 需要持续更新状态时使用，完成项保留证据或结果。 |
| 顺序流程 | 有序列表 | 步骤顺序影响执行结果时使用。 |
| 并列要点 | 无序列表 | 项目同质且不需要字段对齐时使用。 |
| 对比、重复字段或验收证据 | Markdown 表格 | 字段短且需要横向比较时使用；不要把长段落塞进单元格。 |
| 单个状态、决策或风险 | 信息块（短标题加键值字段，必要时使用块引用） | 只突出一个重点，不嵌套信息块，不依赖平台专属卡片语法。 |
| 代码、日志、JSON 和命令输出 | fenced code block | 保留原始缩进、换行和字面量，不转成表格。 |

- 结论或当前状态先于细节；只在信息量和关系复杂度确实需要时增加结构。
- 不使用装饰性卡片、emoji 或嵌套卡片来制造视觉层次；终端不支持信息块时退化为短标题和键值列表。

## 角色边界

- 主 Agent 负责澄清、范围、集成和最终交付说明。
- 实现 Agent 可以报告自己的改动和测试，但不能批准自己创建的高风险工作。
- 测试 Agent 负责证明既定验收标准，不重新定义范围。
- Reviewer 默认只读；已确认问题和仍需证据的风险必须分开记录。
- Codex full 的 Tester 使用 `workspace-write` 仅为允许运行生成忽略缓存的测试；不得留下任何 Git 可见修改。Reviewer 使用只读沙箱和高推理强度，按 findings-first 输出并承担 Red Team。
- 红区变更、未决业务决策和安全决策仍必须有人类确认。

## 多 Agent 与工具使用

默认先用单 Agent；只有上下文隔离或独立交付物带来的收益高于编排成本时才拆分。多 Agent 使用扁平 DAG：只有主 Agent 能派发；child 需要继续拆分时必须以阻塞状态回报，由主 Agent 决定是否创建同级 child。父 Agent 是 `docs/tasks/<任务编号>.md` 控制块、状态和证据的唯一维护者，child 只返回约定的结构化结果。

### 需求分类与默认模式

| 需求类型 | 默认编排 | 判定依据 |
| --- | --- | --- |
| 文档查询、代码定位、只读解释 | 单 Agent | 不创建 child，不生成完整任务图。 |
| 文案修改、局部样式、单页面调整 | 单 Agent | 相邻文件仍由同一上下文完成。 |
| 单模块功能、小型缺陷修复 | 单 Agent | 使用聚焦验证，不因步骤数量拆分。 |
| 跨层但共享契约、共享文件或共享边界较多 | 单 Agent 串行 | 可增加独立 Reviewer，但禁止并行写共享边界。 |
| 复杂可拆且有两个以上独立交付单元 | 多 Agent 候选 | 通过全部准入门禁后自动派发。 |
| 安全、发布、红区或不可逆操作 | 受控模式 | 分析和核验可拆分，执行仍受人工门禁约束。 |

复杂可拆任务只有在存在至少两个可独立验收的工作单元且下列条件全部满足时，才自动启用多 Agent，无需额外确认：

1. 至少两个工作单元可以独立验收，并各自产生明确交付物。
2. 每个 child 的输入、输出、写入范围和依赖可在派发前固定。
3. 同批 child 的写入范围不重叠；共享契约、共享文件或共享边界必须由单 Agent 串行处理。
4. 每个 child 都有确定性、可重复的验证方式，父任务另有 fan-in 后的集成验证。
5. 平台或 adapter 提供真实、原生的子 Agent 能力，且隔离与并行收益高于派发、协调和 fan-in 成本。

以上准入条件必须全部同时满足，才能启用多 Agent；任一条件不满足时记录判定依据并保持单 Agent。用户要求“尽量多用 Agent”或“多用 Agent”不得绕过或替代准入门禁。能力不可用时降级为单 Agent，不得模拟或虚构多 Agent 执行。

新手、标准、专家等交互偏好只调整解释深度和确认频率，不影响风险、安全、验证或编排结论，也不构成用户身份评级或权限等级。自动派发只适用于已授权、可逆且不涉及红区的范围；外部发布、权限变化、破坏性操作和业务歧义仍须人工决定。

派发前必须固定 child ID、最小必要输入、项目相对写入范围、不得修改范围、依赖、冲突、执行批次、时间盒、停止条件、验证命令和输出格式。不得把整段会话或无关计划灌入 child；外部 skill 与工具只补充本地治理，不覆盖仓库指令、红区门禁或验证要求。

### Fan-out / Fan-in

- Fan-out 只适用于交付物独立、写入范围不重叠、依赖关系明确且冲突可预判的子任务。
- 共享文件、共享契约或无法判断冲突时必须串行；并行不等于允许多个 Agent 同时修改同一边界。
- Child 遇到越界、依赖未满足、需要再拆分或无法验证时返回阻塞状态，不自行扩大范围或再委派。
- Fan-in 由主 Agent 负责核对实际 diff 与自报证据、汇总、去重、处理冲突、持久化任务状态、审查最终 diff，并在目标工作区重新运行受影响验证。
- Fan-in 不得把多个独立目的重新合并成不可审查的大提交；每个子任务的 report 和验证证据必须保留。

普通实现步骤、进度更新和既定验证命令不需要逐步确认。不可逆操作、范围或外部契约变化、红区、高风险门禁、规则冲突和缺少用户专有信息时才停止并请求确认。

## 交接

v3 交接只写在父 Agent 维护的同一任务 Markdown，不创建平行 workflow/report 文件。`交接记录` JSON 每条固定包含版本、编号、类型、来源/目标角色、Agent/运行收据、状态、变更集指纹、已完成/未完成、验证证据、未验证项、风险、下一步、恢复提示和时间。类型只允许 `阶段交接`、`子任务回传`、`暂停恢复`；状态只允许 `待接收`、`已接收`、`已返回`、`阻塞`。每个编号从 `待接收` 开始，身份字段在后续状态中不可改变。

`SubagentStart` 保存 v2 项目内收据：哈希化 session/agent/turn ID、角色、时间、冻结变更集与受保护任务/审查证据指纹；同一运行身份使用稳定 key 与 exclusive create 原子保证只允许一份收据，重核验必须使用新 turn。`SubagentStop` 校验固定输出字段和角色结论，只有缺字段、重复字段或不可识别状态才最多续跑一次；结构完整的负面结论直接终止。只有 Tester `通过` 与 Reviewer `批准` 可合格封存。收据不保存 prompt、transcript 或模型原文。项目内哈希用于检测错配、重复、路径穿越、结构异常和意外漂移，不宣称能抵御已拥有工作区写权限的恶意进程；v3 单任务和父任务的集成命令证据必须晚于两份收据完成时间。人工等价证据必须是项目内非空常规文件。

快速任务可精简交付，但不能省略未验证项和后续动作；不得用 memory、Handoff、角色安装状态或 child 自报绕过实际 diff 检查、父级集成验证或独立审查。

## 完成标准

完成必须有来自当前工作区的证据；高风险工作必须有可追责 reviewer；交付包必须区分已验证结果和剩余风险。
