# 项目目录规则

项目目录规则记录所有权和依赖方向，让 Agent 能定位正确变更边界，而不是临时发明新结构。

## 发现顺序

1. 读取仓库入口指令；存在当前状态和架构文档时一并读取。
2. 检查 package/workspace manifest、构建入口、adapter 和模块索引。
3. 项目内已有代码结构索引工具时先确认索引状态并用于结构化定位；否则使用仓库搜索。
4. 编辑前确认与变更范围对应的测试和验证命令。

## 放置规则

- 领域行为放在拥有对应状态和接口的领域内。
- 共享目录只放已被多个消费者验证可复用的能力，不作为临时堆放区。
- Adapter 只负责外部与内部契约转换，不拥有业务规则。
- 生成物、vendored、构建、缓存、证据和临时目录都不是源码所有权位置。
- 新增顶层目录必须有架构理由、owner 和依赖方向说明。

## 文档与 ADR

- 文档先找到单一来源和既有格式，避免创建第二套真值。
- 面向读者记录当前事实、操作步骤和可验证命令；临时实现流水账不进入耐久文档。
- ADR 遵循目标项目既有制度；没有既有制度时，不为普通修复、局部重命名、可逆实现选择或短期实验新建 ADR 体系。
- 只有长期有效、高影响且难以逆转的架构、公共契约、安全、可靠性、关键依赖或迁移决策才需要正式 ADR；以影响持续时间、消费方范围、迁移成本和回滚难度判断，不以文件数量判断。
- Vibe-Harness 自身的正式 ADR 来源是 docs/adr/，每个决策一个 ADR-0000-short-title.md 文件，并通过 docs/adr/catalog.json 建立索引。
- Vibe-Harness ADR 包含上下文、决策驱动、备选、结果、后果、确认方式、状态、责任人和复核条件；accepted 和 rejected ADR 不直接改写，替代决策通过 supersedes / supersededBy 关联。
- docs/memory/DECISIONS.md 只保存正式 ADR 的 ID、状态、摘要和链接；memory/decisions.md 只保存运行态恢复信息，二者都不替代正式 ADR。

## 跨边界变更

变更跨模块、package、仓库或服务时，列出每个 owner 和接口，识别兼容与回滚策略，并验证两侧。所有权仍不清晰时停在澄清阶段，不把逻辑散落到多层。

## 完整项目分析

仅在用户明确要求完整项目分析，或跨模块、跨服务、公共契约的影响范围无法缩小时，补充以下内容：技术栈（语言、框架、构建工具和核心依赖版本）、目录结构（核心目录职责和关键配置）、业务流（入口、处理层级和输出）、数据流（来源、处理节点和存储或展示位置）、模块依赖（关键耦合和依赖链）。小型 Bug、单文件修改和简单问答不展开该清单。

## 完成标准

只有当新增和修改文件都位于声明的所有权边界内、import 遵循预期方向、测试能证明受影响消费者时，变更才算完成。
