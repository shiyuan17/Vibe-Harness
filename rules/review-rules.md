# Review Rules

Review 优先关注 bug、回归、测试缺口、安全风险和规则违规。

## 输入

- 用户请求、Spec、Plan 或 Task。
- 当前 diff、目标分支和相关上下文。
- 工作流交付包、风险等级和红区确认状态。
- 验证证据：命令、退出码、关键输出、截图或人工核对。

## 输出

- 问题列表，按严重度排序。
- 已核对验证和未覆盖风险。
- 待确认问题。
- 审查结论：`Approve` / `Request changes` / `Blocked by missing evidence`。

## Finding 格式

每条 finding 包含：

- 严重度：`Critical` / `High` / `Medium` / `Low`。
- 位置：文件和行号，或无法定位时说明原因。
- 问题：可触发的 bug、回归、安全风险、测试缺口或规则违规。
- 影响：用户可见行为、数据、安全、发布或维护成本。
- 建议：最小修复方向或需要补充的证据。

## 问题优先

先列问题，再写摘要。代码审查时按严重程度排序，并尽量包含文件/行号引用。

## 独立判断

高风险工作需要独立于实现者的审查者。审查者核对 diff、范围、测试和工作流交付包。审查通过不替代红区人工确认。

## 无问题

如果没有发现问题，要明确说明，并补充剩余测试缺口或残余风险。

无 finding 输出仍必须列出已核对范围、已读证据、未运行验证和残余风险，不能只写“LGTM”。

## 阻断条件

- `Critical` / `High` 问题未处理。
- 验证证据缺失，或不能覆盖验收标准。
- 红区人工确认缺失。
- 实现者自证高风险最终通过。
- diff 范围不清，存在可能覆盖用户无关改动的风险。
- 目标项目的项目专属规则、验证命令或 VCS 状态未纳入审查依据。
