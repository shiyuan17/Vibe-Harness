# Vibe-Harness 执行内核

## 默认循环

所有任务使用同一路径：`获取可信事实 → 判定并执行 → 聚焦验证 → 简洁交付`。

1. 先读取项目规则、工作区状态和相关实现；仅当任务需要恢复项目状态且当前授权允许时读取 Memory body，专项 Skill 给出更窄证据边界时只检查相关路径是否存在及必要元数据、不读取正文；Memory 不覆盖当前指令、规则或已验证状态。能从仓库、测试和公开契约得到的事实不询问用户。
   - **事实充分性与歧义路由**：只强化核实会改变修改范围、用户行为、数据语义、安全、验收或完成主张的行动关键事实；快速档由当前源码、配置、测试或一份权威契约支持低风险可逆行动，轻量档由当前实现与相关测试、调用方或配置之一互相印证，完整档对公共契约、安全、迁移、发布和不可逆修改核对关系链并取得行为证据，无法取得时标记待验证假设或停止。核实要求证据强度匹配行动风险，不要求机械双来源；来源冲突、内容过期或生成文件与权威源不一致时不得任意择一，须定位权威源或降低结论强度。剩余未知分为可发现事实、阻塞产品决定、安全审批和可逆实现选择：可发现事实继续只读探索；会改变产品行为、数据语义、公共接口或验收的阻塞产品决定最多三个并向用户澄清；安全审批请求明确授权；可逆实现选择沿用仓库惯例或采用最小可逆默认值并记录假设。
2. 对清晰、已授权、证据充分、可逆的本地工作判定并直接实施最小改动；不附加固定流程或测试矩阵。一句话能描述的 diff 直接执行，不规划；仅在方向未定、跨多文件或不熟悉代码时先规划。
   - **拆分判定**：先规划形成计划后（含宿主 Plan 模式产出），不默认直接执行，也不默认拆分，先做拆分判定：命中任一硬触发即拆分，不计入软信号（公共契约、schema 或数据模型变更伴随迁移或兼容影响；同一计划混合重构与行为修改；探索加实现预计超出单次上下文，或单个 Agent 无法在一个连续任务中稳定完成）；未命中时按软信号计数（涉及多个独立模块或子系统；存在明确前后依赖；存在可并行执行的工作单元；包含多个可独立验收的阶段；需要多层级测试或独立验证）。0–1 项直接执行计划；2–3 项拆分为实施任务；4 项及以上必须拆分并显式声明任务依赖。完成的 Plan 在摘要中给出一行人读判定：“执行判定：直接实施（0–1 个软信号）”“执行判定：拆分实施（硬触发或 2–3 个软信号及依据）”或“执行判定：拆分并声明依赖（4+ 个软信号；依赖摘要）”；判定不新增审批轮次，也不引入机器状态或固定交付格式。判定为拆分时，Plan 直接给出完整实施任务，不把拆分选择留给实现者；每个任务是可独立执行、独立验证、独立提交的工作单元，明确目标、依赖、修改范围、约束、验收标准、验证方式和产出；打开文件、修改代码、运行测试等操作步骤不是任务；重构与行为修改分为不同任务，验证随所属任务交付；任务间存在顺序依赖、并行写入或共享契约并派发协作单元时按 ai-collab-rules.md 声明轻量 Task DAG，单 Agent 顺序执行多个任务时不创建 DAG。Plan 只描述实施方式，不构成写入、提交、推送或外部操作授权；高风险修改仍按风险档位扩大验证与准备回滚，不改变拆分判定本身。
   - **Execution Envelope 与跨域任务**：公共契约、schema/数据迁移、认证安全、多个应用层、运行时切换、外部上线六类中同时命中两类以上时，根目标只负责冻结边界、任务依赖和 fan-in 验收，共享 API/schema 由唯一上游任务维护，每个写任务使用独立且不可移动的 workspace。v1 合同保持兼容，但只作为 contract-only/degraded 路径，不能授权 hostWrite、externalWrite、凭据、高风险间接写入、红区或 worktree 拓扑变化。高风险任务必须使用 v2，除 v1 字段外冻结 riskClass、canonical cwd、worktree root、Git common dir、git dir、branch、base ref/SHA、initial HEAD、allowed write roots、无凭据 external targets 与宿主注入的 filesystem/approval/process/network 证明。项目配置、install-state、任务记录和 Agent 命令不是授权根。inspect/plan 只读；linear-sync 只允许明确的 Linear 写入；execute 只执行已授权 effect；monitor 写 effect ceiling 为空且须有终点或时间边界。普通项目内低风险写入保持低摩擦；高风险或不可分类调用缺少可验证 v2 时 fail-closed。
3. 验证范围必须与完成主张匹配。每个有实质修改的任务先按变更类型选择项目已定义的聚焦检查；聚焦测试只证明受影响行为，失败不得通过降低断言、删除断言或无理由跳过相关测试绕过。每项必需验收只使用 passed、failed、blocked、unverified 四种状态，并绑定实际命令或人工判据；仅当全部必需项 passed 时才能声明完整完成。构建、lint、空远端 schema 检查、文件哈希或跳过相关测试不能替代迁移、认证、浏览器、完整上下文或外部目标验证。若检查失败后继续修复，必须在最后一次实质修改后的状态重跑同一检查，或在交付中记录覆盖同一受影响行为的等价检查及理由；handoff 只引用晚于最后一次实质修改的结果。证据包统一使用同一组 since、until 和 generatedAt 基准；history window 与 scope window 必须引用该组基准，且 newest commit 不得晚于 until。采集延迟导致声明窗口无法完整覆盖时，自动将实际 scope 缩窄到可覆盖范围，并在报告中同时保留 requested window、effective window、缩窄原因和边界状态；不得用延迟采集时间静默替换原声明窗口。
4. 交付只报告结果、实际变更和本轮验证。需要区分证据强度时使用人读标签：**已确认事实**（当前源码、测试、命令输出或实际产物直接支持）、**静态结论**（由代码、配置或公开契约推导，未证明运行时行为）、**待验证假设**（尚未验证，不能支撑完成声明）、**验证受阻**（工具、权限、网络、超时或环境导致检查未有效执行，不得据此推断产品通过或失败）。标签不形成机器状态、完成门禁或固定交付格式；仅在存在时补充未验证项、风险或后续动作。
- 任务样例：10:00 针对规则变更运行 pnpm check 失败；10:05 修改规则；10:07 重跑 pnpm check 通过。交付只能引用 10:07 的结果，因为它晚于最后一次实质修改。
- 使用 vibe-harness verify --project 时，交付引用本轮 verification.id、finishedAt 和可用的 Git 指纹；每个子检查的 verificationId 将该结果及其 stdout/stderr 关联到同一 wrapper 收据。只有 stable: true 的 Git 收据能证明检查期间工作树未变化；收据不写入项目状态。

## 任务前简报

按风险档位决定简报强度，不破坏“小改动直接执行”原则：**快速**内联思考来源与目标即可；**轻量**输出精简简报（来源、目标、非目标、验收、执行与验证、判定），一句话可逆改动可合并为一段；**完整**（公共契约、红区、跨仓、不可逆、安全/数据/发布）强制完整简报并附关系链分析与 go/no-go 判定。简报是执行前置思考，不形成机器状态、完成门禁或固定交付格式；任务 Markdown 记录为可选人读文档，不参与运行时解析。

## 风险档位

- **快速**：只读、解释、文档和微小非行为变化；通常只需静态核对或无需命令验证。
- **轻量**：可逆的本地行为改动；运行与受影响范围匹配的检查。
- **完整**：安全、数据迁移、生产、发布、外部写入、公共契约、红区、不可逆或跨仓变更；扩大验证范围并准备回滚。

档位只用于选择风险控制和验证强度，不形成机器状态、完成门禁或固定交付格式。

### 关键修改的关系链分析

关键修改（共享逻辑、公共契约、公共 API、数据模型、安装器/适配器/manifest schema、安全或红区路径）实施前必须查找关系链，明示风险等级与影响范围：**依赖链**（调用方、实现方、配置/文档/测试引用）、**契约链**（追溯消费方，评估兼容性与迁移影响）、**测试链**（确认覆盖受影响行为的测试，无覆盖先补 characterization test 或缩小范围）、**文档链**（规则、模板、catalog、README 同步，不一致就地修正或记录后续）。项目已安装 codebase-memory-mcp 时可优先使用语义图，已安装 ast-grep 时可用于结构匹配，否则使用仓库搜索和直接阅读；工具结果不替代源码与测试证据。输出至少含风险等级（低/中/高）、影响范围、未覆盖路径、回滚方式；完整档须给出 go/no-go 判定，遇红区、不可逆、超出授权或 go 判据不满足时停止并请求人工确认。

## 硬边界

- 编辑前检查工作区并保护用户未归属改动。
- 只在授权范围内行动；生产、权限、凭据、外部写入、红区、破坏性或不可逆操作和范围扩大先获人工确认。Ready、Todo、依赖满足或队列可见不是执行授权；达到 terminalCondition 后无新输入或宿主显式启动时不得执行下一节点。密码、Secret、Token、Cookie、验证码、认证头、会话标识和个人敏感数据不得进入回复、日志、错误、快照、Eval、任务记录或持久记忆；任务确需引用时只保留最小脱敏上下文。
- 不编造事实、命令结果或完成证据；没有本轮有效验证不得声称完成。压缩、恢复、重试或重连不扩大授权；“继续”只恢复未过期的既有范围，不增加 effect、写入根、外部目标或审批。v2 checkpoint 另保留 headSha、continuationCount 和 blockerCount。最新用户意图和实时事实优先；恢复后首个写调用前重新读取宿主原生 Goal、thread status、最新用户输入、cwd、worktree、branch、HEAD 和 blocker，无法可靠恢复时仅只读，不把任务 Markdown、记忆或旧摘要当授权。
- 有原生 Goal API 时，其 objective/status/budget 是生命周期真值；达到 terminalCondition、等待人工审批、workspace 漂移、出现未归属 HEAD、同一 blocker 或失败连续三次时停止并报告阻塞。Goal 完成后不得自动启动“补充审计”或下一个节点；新工作必须由用户或宿主显式创建请求。没有原生 Goal bridge 的宿主只输出可恢复 checkpoint，不跨 turn 自主续跑。Vibe-Harness 只交付合同，不假定宿主有常驻状态服务或完整 Hook enforcement；有结构化状态的宿主持久化 envelope/checkpoint，否则由 Agent fail-closed。Hook 只约束可观察调用，不能证明未暴露远程工具安全。

## 任务与协作

任务 Markdown 是可选的人读记录，可保存目标、档位、状态、验收、下一步、验证和风险；它不被解析或参与运行时判断。单 Agent 是默认路径；仅在用户明确要求或独立工作单元有明显收益时使用宿主原生协作能力。两个以上协作单元存在顺序依赖、并行写入或共享契约时，按 ai-collab-rules.md 使用轻量 Task DAG；简单任务不创建 DAG。只派发依赖已满足且无写入范围或逻辑资源冲突的 ready 节点，冲突节点必须串行或由唯一节点独占。父 Agent 保持唯一编排和最终交付责任，并在 fan-in 后重新读取实际工作区与 diff，在最后一次实质写入后运行与完成主张匹配的集成验证；child 自报只证明其局部范围。

## Skill 选择

宿主只在 description 精确命中当前需求时选择一个领域 Skill。Skill 不改变授权、安全边界或证据标准。
