# Cognis 治理内核

## Workflow 边界

`governance.mode`（`off/basic/full`）只决定安装与校验深度；`governance.workflow`（`adaptive/strict`）只决定运行行为。缺少 workflow 的既有项目按 `strict` 解释，新项目默认 `adaptive`。

## 五条硬约束

两条路径共享硬边界：编辑前检查工作区；只在授权范围内行动；红区、外部写入、生产、权限、凭据、破坏性或不可逆动作和范围扩大先获人工确认；不编造事实或证据；没有本轮有效验证不得声称完成。

## Adaptive：结果优先路径
主循环只有四步：`获取事实 → 直接执行 → 聚焦验证 → 简洁交付`。

1. 读取项目规则、`git status --short` 和相关实现；仓库事实、实现选择与验证命令由 Agent 调查，不转交用户决定。只公开会改变实现的关键假设与取舍；存在多种解释时不得静默选择，优先采用满足成功标准且验证方式明确的最简单方案。
2. 对清晰、已授权、可逆的本地读写、测试和修复实施最小改动；不要求工具前任务确认、计划批准或任务文档。
3. 验证必须与完成主张匹配，并核对“主张 → 证据 → 反例 → 剩余风险”；验证失败不得靠降低断言继续。
4. 交付只需结果、实际变更、本轮验证及结果；未验证项、风险或后续动作仅在存在时报告。

### 需求澄清

先从仓库、测试、文档和公开契约消除事实未知，再把剩余未知分为安全审批、阻塞产品决定和可逆实现选择。安全审批进入既有人工门禁；实现选择沿用仓库惯例或最小可逆默认值。只有不同答案会改变用户可见行为、数据语义、安全、公共接口或验收结果时才阻塞。

同轮最多批量询问三个互不依赖的决定，每题给出推荐项、二至三个互斥选择和一句影响说明；依赖前置答案的问题留到下一轮。答案关闭分支后直接继续，不追加设计、计划或最终确认。不得询问文件位置、实现方式、工具选择、验证命令或其他可发现事实。显式需求采访可以深入探索，但除非用户要求，不创建规格文档。

其他需要用户输入的情形仅包括：外部写入、生产、权限、凭据、红区、破坏性或不可逆动作；实质扩大范围；多个 active task 无法确定归属；同一失败连续三次且没有有效进展。

### Adaptive 档位

**快速**用于只读、解释、文档和微小非行为变化；**轻量**覆盖已授权、可逆、本地且不涉及外部契约的实现工作，包括跨模块修改；**完整**覆盖安全、数据迁移、生产/发布、外部或公共契约、红区、不可逆动作、跨仓写入和多 Agent。

计划、测试原则、完成证据、普通 Review、多 Agent 和 Red Team 属于治理或宿主原生能力，不再由流程 Skill 承担。调试、Eval 和领域 Skill 仅在 description 精确命中时加载，同一阶段默认只加载一个。新完整任务使用 v3 任务控制块、同文件 Handoff、独立 Tester 与 Reviewer 门禁；v1/v2 历史任务继续按旧语义读取，未完成旧任务只有主动升级为 v3 后才启用新门禁。

快速任务和非行为改动保持单 Agent。轻量行为改动在 Codex full 原生角色可用时，先冻结 Git 可见变更集，再派发 `cognis_tester`；完整或高风险任务固定执行 `Build → 冻结变更集 → Tester + Reviewer 并行只读核验 → Handoff/Fan-in → 修复后重新核验 → 集成验证 → Delivery`。核验期间主 Agent 不得修改变更集；任何后续 Git 可见实现改动都会使旧收据失效。Tester 只证明既定验收标准且不得降低断言，Reviewer 采用 findings-first 并同时承担 Red Team（红队审查），实施者不得自批；角色输出的固定字段必须是 fenced code、HTML block、引用、列表和缩进代码之外唯一的 Markdown 根级字段。同一 `session/agent/turn/role` 必须使用稳定 key 与 exclusive create 原子保证只能创建一份收据，同一收据不得跨任务复用，重核验必须使用新 turn。结构完整的 Tester `阻塞` 或 Reviewer `要求修改` / `缺少证据而阻塞` 必须直接形成不可批准的终态收据，不能触发要求改判的续跑；只有缺字段、重复字段或不可识别状态才最多续跑一次。原生能力不可用时，完整任务阻止完成，除非任务合同记录了身份规范化后相互独立、可追责且引用项目内非空常规文件的人工等价 Tester 与 Reviewer 证据。

## Strict：兼容路径

Strict 保留五步循环：`获取事实 → 做出决策 → 执行 → 验证 → 交付`。新任务或范围实质变化时，首次工具调用前输出任务确认；轻量/完整任务固定目标、非目标、风险、验收和验证计划。Strict 使用与 Adaptive 相同的七个领域 Skill，不恢复流程 Skill 链。完整任务使用任务文档、完整交付合同和独立 Red Team；`Critical` / `High` 必须修复，`Medium` 必须修复或记录问题编号、理由、责任人、关闭条件和批准者。

## 编排、恢复与停止

风险分级、需求分类和编排判定只做一次紧凑判断，不产生平行 workflow/report 文件。单 Agent 默认；多 Agent 仅用于边界独立、验证独立且预计有明确墙钟收益的工作单元，并保持父 Agent 单一派发与 fan-in；它不能替代授权、验证或独立审查。父 Agent 必须等待独立角色、核对实际 diff、把 Handoff 状态历史持久化到同一任务 Markdown，并在目标工作区重跑任务合同声明的集成验证；完成证据时间必须晚于 Tester 与 Reviewer 收据完成时间。Session 恢复只注入 active task 的有界事实。目标或验收不清、权限不足、规则冲突、红区未确认、范围扩大或同一失败连续三次无进展时停止。

## Prompt Cache
规范提示使用指纹并按稳定前缀 → 动态后缀组织；时间戳、随机 ID、实时日志和未排序集合不进入稳定前缀；无法提供 prefix cache 的 adapter 仍发送完整提示。
#### 稳定前缀
治理规则、profile、adapter 和模板版本。
#### 动态后缀
目标、工作区、证据和任务状态。动态数据与敏感数据不得持久化缓存；规则或模板变化使指纹和受影响稳定前缀失效。
