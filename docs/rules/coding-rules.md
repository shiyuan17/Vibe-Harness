# 编码规则

编码规则强调小、清晰、可审查、可验证的变更。优先复用仓库既有模式；只有在确实降低复杂度或匹配既有边界时才新增抽象。

## 规则

- 优先复用本仓库既有模式，避免为一次性需求引入抽象。
- 不增加用户未要求的功能、配置项、扩展点或兼容层；不处理理论上不可能出现的分支。
- 一个任务只解决一个问题，并使用一组可独立验证的验收标准描述完成边界。
- 一个 commit 只表达一个逻辑目的；重构、格式化、依赖升级和业务修改默认拆分。
- 格式化或机械重写不得与业务修改混在同一提交；确有必要时，在交付记录说明原因和影响。
- 不顺手修改无关代码；发现无关清理项时记录为后续任务，不直接带入当前变更。
- 每个变更文件和关键代码行必须能追溯到任务目标或验收标准。
- 共享逻辑变更必须配套聚焦测试，并说明影响范围。
- 交付时写清影响范围、验证命令和未覆盖风险。

## 检查清单

- 范围：只改当前任务需要的文件，不夹带无关重构。
- 模式：优先复用已有工具、目录结构、命名和错误处理方式。
- 抽象：只有在减少真实重复或匹配既有边界时新增抽象。
- 清理：只删除本次改动直接产生的无用 import、变量、函数和文件；既有无关死代码仅报告，不擅自删除。
- 收尾清理：交付前清点本次会话残留的一次性计划文档、调试脚本和被替代的旧副本；仍有效的内容先并入正式文档，已失效的逐条标注理由列入删除候选交用户确认，未确认前不删。
- 精简：先用现有测试和调用方锁定行为；删除重复、无效间接层、死代码和不再需要的兼容分支时，每次只做一个可审查的结构变化。
- 复杂度：实现明显大于需求所需时，先简化再交付。
- 变更大小：不以固定行数作为硬性门禁，以能否独立审查、验证和回滚为判断标准。
- 依赖：新增依赖前确认现有栈不能解决、维护状态、体积、许可证和漏洞。
- 测试：共享逻辑、bugfix 和行为变化必须有聚焦测试或明确人工核对；无法证明行为等价时先缩小范围或补 characterization test。

## 验证证据

- lint、typecheck、聚焦测试和必要的全量测试命令。
- 影响范围和未覆盖路径。
- 精简或重构交付需写清保留的契约、删除内容和未覆盖风险。
- 新依赖的理由；没有新增依赖时写明复用方式。

## 停止条件

需求、边界、依赖许可或验证方式不清时停止；不得用“先实现再说”替代计划。
