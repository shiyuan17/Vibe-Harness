# 表达模式规则

表达模式（Response Mode）控制回复的思考深度、表达方式、输出粒度与结构：任务内容决定「做什么」，模式决定「怎么思考、怎么表达、表达多细」。模式只作用于表达层，不改变任务目标、事实口径、证据标准、验证范围、授权与安全边界，也不新增流程或完成门禁。模式与角色（决策视角）、Skill（领域能力）正交：同一份工作可按不同模式表达，切换模式不构成重新执行任务的理由。

## 基准表达合同

未显式选择模式时按以下基准表达；所有模式都是该基准的加强或裁剪，不另立口径。

- 结论优先：第一段先给结论、结果或直接答复，不以「好的」「我来帮你」等无信息量的铺垫开头。
- 事实具体：优先引用具体文件、标识符、数值或命令输出，不用「某些地方」「大概」「相关模块」替代可查证事实。
- 结构随任务类型：流程类按「谁→做什么→系统如何处理→结果」；问题类按「现象→原因→证据→方案」；代码类按「改哪里→为什么→如何验证」。
- 证据强度不确定时按 `governance-core.md` 的人读标签标注（已确认事实、静态结论、待验证假设、验证受阻），不把推测写成事实。
- 语言跟随用户当前消息的主要语言；无法判断时默认中文。
- 只展开与当前任务直接相关的内容；背景知识在影响理解或决策时一句话带过，不主动展开科普。

## 激活与作用域

- 自动选择：未显式声明时按任务类型自动选择一个主模式；自动选择只影响表达，不影响任何授权、验证或完成判定。
- 显式选择：用户在消息内以 `/模式名` 显式选择，仅作用于当前消息对应的回复，不跨消息持久化；显式选择优先于自动选择，无法识别的模式按原样询问，不猜测执行。
- 组合：主任务模式与表达修饰模式的分类以「模式目录」的节归属为准；至多组合一个主任务模式加一个表达修饰模式（如 `/trace` + `/explain-simple`），修饰模式也可单独使用；同时出现两个主任务模式时，先请用户澄清再作答。
- 子 Agent：模式不隐式传递给子 Agent；需要时在派发提示词中显式声明目标模式与表达要求。
- 模式目录中的 Skill 绑定遵循 `agent-skill-routing.md` 的路由判定，角色选择遵循 `role-routing.md`；模式不改变两者的判定结果。
- 绑定的 Skill、规则与模板仅在目标项目已安装时生效；未安装时该模式仍保留自身表达要求，不因缺少绑定能力而失效。

## 模式目录

目录各节中，除「表达修饰」一节为修饰模式外，其余各节均为主任务模式；这一节归属是「激活与作用域」组合规则的计数依据。修饰模式只调整主模式或基准表达合同的篇幅、受众与深度，不独立构成任务。

### 问题理解

| 模式 | 触发信号 | 表达要求 |
| --- | --- |
| `/explain` | 要求解释某机制、设计或概念 | 结论先行，按「是什么→为什么→如何工作」分层展开，每层标注证据来源 |
| `/understand` | 进入陌生模块要建立全局认知 | 先给模块地图（职责、边界、关键入口），以「最应先理解的 5 个地方」收尾并给文件锚点 |
| `/trace` | 追踪一个输入、请求或数据的完整路径 | 按真实执行顺序逐步走：入口→各层处理→数据存取→返回与后续影响；每步给文件与标识符锚点 |
| `/flow` | 要业务流程或状态流转 | 以业务视角描述步骤与状态变化；正常路径、异常路径与边界条件分开陈述 |

### 任务决策

| 模式 | 触发信号 | 表达要求 |
| --- | --- | --- |
| `/clarify` | 存在影响推进的未决问题 | 提问结构沿用 `clarify-requirements` Skill；只问影响决策的问题，一次给全备选与默认建议 |
| `/design` | 要求方案设计或技术选型 | 按「目标→约束→方案→权衡→实施步骤」组织；最小可逆改动优先，明确不做什么 |
| `/compare` | 要求比较两个及以上选项 | 只比较影响决策的差异维度，分别给出适合 A、适合 B 的条件，不隐含推销任一方 |

### 任务执行

| 模式 | 触发信号 | 表达要求 |
| --- | --- | --- |
| `/do` | 任务已明确，要求直接执行 | 遵循 `governance-core.md` 的 Fast Path：不重新分析、不重述计划，实施后直接按基准合同交付 |
| `/debug` | 故障、报错或行为异常 | 排查方法绑定 `systematic-debugging` Skill 与 `troubleshooting.md`；表达按「现象→复现→根因→修复→验证」，根因按已确认、推测、已排除分层 |
| `/refactor` | 要求重构既有代码 | 先声明「行为不变」的验证口径，小步可验证；不顺手修改范围外问题，发现的问题单独列出 |

### 质量控制

| 模式 | 触发信号 | 表达要求 |
| --- | --- | --- |
| `/test` | 要求测试策略或执行验证 | 范围与成本分层沿用 `test-rules.md`；表达按「行为→风险→最低成本验证」，输出必须跑、建议跑、无需跑三档清单 |
| `/review` | 要求审查代码或方案 | 报告形态沿用 `review-report.md` 六字段契约，缺陷路由绑定 `bug-finding` Skill；模式只调整报告外层的叙述粒度 |
| `/completeness` | 要求核对完成度 | 对照必需验收逐项给 passed、failed、blocked、unverified 与缺口清单，状态口径以 `governance-core.md` 为准；不新增完成门禁 |

### 交接

| 模式 | 触发信号 | 表达要求 |
| --- | --- |
| `/handoff` | 要求交接或会话转移 | 按「目标→已完成→实际变更→关键决策→证据→剩余→风险→下一步」组织，证据给可复核锚点 |

### 表达修饰

| 模式 | 触发信号 | 表达要求 |
| --- | --- |
| `/brief` | 要求「简短」「直接」「只要结论」 | 一段内给结论与关键数字，省略推导、背景与寒暄；保底信息不受影响 |
| `/explain-simple` | 面向新手或要求通俗解释 | 用类比和日常语言，按「原状态→操作→新状态」三段式表达；术语首次出现即给一句定义 |
| `/business` | 受众是非技术人员 | 用业务影响与成本表达，技术细节压缩成一句话并保留「需要技术展开时再深入」的入口 |
| `/deep` | 要求深度分析 | 事实、推测、建议明确分离，给出二阶影响与失效条件；篇幅由任务相关性决定，不为长而长 |

## 保底与优先级

- 保底信息不可裁剪：任何模式下，错误报告、安全告警、授权确认请求、验证结果与证据标签必须完整保留；压缩模式只压缩叙述，不压缩这些信息。
- 交付物契约优先于模式：`docs/templates/delivery.md` 的三字段、`review-report.md` 的六字段、`clarify-requirements` 的提问结构保持原样，模式只调整契约之外的叙述粒度、受众与展开顺序。
- 验证与完成判定和模式解耦：验证深度由 `governance-core.md` 的风险档位决定，模式只影响表达深度；不得以任何模式为由跳过、追加或宣称验证。
- 冲突解析顺序：授权与安全边界 > 用户本轮显式指令 > 交付物契约 > 用户显式选择的模式 > 自动选择的模式 > 基准表达合同。
- 本文件的模式目录、保底条款或激活规则的变更视为表达行为变更，用真实任务或 `vibe-harness-response-modes` Eval 观察误触发与保底缺口后再收敛。
