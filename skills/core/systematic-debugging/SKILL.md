# 系统化调试

不要先猜修复。先复现、定位根因、验证假设，再实施最小修复。

## 硬规则

```text
NO FIXES WITHOUT ROOT CAUSE
```

没有解释清楚“为什么会发生”，就不要改代码。

## 四阶段

1. 根因调查
   - 复现问题，记录输入、环境和实际输出。
   - 找到直接失败点：错误、断言、异常、错误 UI 或错误数据。
   - 沿调用链向上追踪到原始触发点。
2. 模式分析
   - 检查同类路径是否也有问题。
   - 区分单点 bug、契约不一致、状态污染、竞态或环境问题。
3. 假设验证
   - 写出可证伪假设。
   - 用日志、断点、最小测试或二分法验证。
   - 一次只验证一个变量。
4. 实施修复
   - 先写能复现问题的失败测试。
   - 做最小修复。
   - 运行回归测试和相关验证。

## 何时读取辅助资料

- 调用链复杂或找不到原始触发点：读 `root-cause-tracing.md`。
- 异步等待或 flaky 测试：读 `condition-based-waiting.md`。
- 需要多层保护验证：读 `defense-in-depth.md`。
- 怀疑测试污染：使用 `find-polluter.sh`。

## 红旗

- “可能是 X”，然后直接改。
- 只修报错行，不追踪是谁传入坏数据。
- 同时改多个可疑点。
- 没有复现步骤或回归测试。
- 用固定 sleep 处理异步问题。
- 测试通过一次就认为 flaky 已修。
- 已经尝试两次修复仍想“再试一个”。

## 常见借口

| 借口 | 现实 |
| --- | --- |
| 先快速修一下 | 未知根因的修复会制造新症状。 |
| 错误行很明显 | 错误行通常只是症状，坏输入来源才是根因。 |
| 同时改几个点更快 | 多变量会让验证失去意义。 |
| flaky 无法复现 | 先收集条件、日志和触发范围，不用固定等待掩盖问题。 |

## 输出

调试结论应包含：

- 症状和复现方式。
- 根因和证据。
- 修复点和为什么是最小修复。
- 回归测试与验证命令。
- 仍可能存在的风险。
