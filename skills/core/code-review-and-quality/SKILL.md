# 代码审查与质量

审查目标是发现会影响行为、安全、数据、发布或长期维护的问题，不是表达风格偏好。

请求审查时附上目标、范围、风险、验证命令、未覆盖项和重点关注问题。若 `ocr` CLI 可执行，先运行 `ocr llm test`，再按目标 diff 调用 `ocr review --audience agent`；CLI、LLM 或凭据不可用时回退到本 Skill 或独立人工审查，并记录缺口。不得输出或硬编码 API key。完整参数见 `references/cli.md`。

## 输入

读取任务/规格、目标 diff、项目规则、风险档位和最新验证证据。范围不清或实现者试图自批高风险工作时阻断。

## 审查

1. 规格符合性：需求、边界、错误路径和非目标是否一致。
2. 正确性：空值、并发、状态转换、回归和测试有效性。
3. 架构与简洁性：依赖方向、既有模式、重复、死代码和无效抽象。
4. 安全与数据：输入边界、认证授权、secret、注入和敏感输出。
5. 性能与 UI：无界工作、阻塞、N+1、重渲染、可访问性和运行时状态。
6. 证据：测试/build/浏览器/接口证据是否覆盖验收，而非只看退出码。

## 输出

findings 优先，按 `Critical`、`High`、`Medium`、`Low` 排序；每项包含文件行号、触发方式、影响和最小修复方向。无 findings 也要说明已核对范围、未验证项和残余风险。

分别给出：

- 规格符合性：`Pass` / `Fail` / `Cannot verify`。
- 代码质量：`Approved` / `Request changes` / `Blocked by evidence`。

Critical/High、证据缺失、红区确认缺失或 diff 归属不清均阻断批准。
