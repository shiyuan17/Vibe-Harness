# 代码审查与质量

审查目标不是挑风格偏好，而是判断变更是否让代码库更健康、更安全、更可维护。

## 使用时机

- 合并 PR 或工作区变更前。
- 完成功能、bugfix 或重构后。
- 需要评估 agent 产出或人工变更时。
- 高风险、共享模块或安全相关变更。

## 五轴审查

1. 正确性
   - 是否满足规格和验收标准。
   - 边界值、空值、错误路径和并发状态是否处理。
   - 测试是否覆盖真实行为。
2. 可读性与简洁性
   - 命名是否清楚并符合项目惯例。
   - 控制流是否直观，是否有不必要抽象。
   - 是否留下 dead code、兼容残骸或无意义注释。
3. 架构
   - 是否符合现有模式和模块边界。
   - 依赖方向是否正确，是否引入循环或耦合。
   - 抽象是否真的降低复杂度。
4. 安全
   - 输入是否在边界校验。
   - secret 是否泄露到代码、日志或版本库。
   - auth、权限、注入、XSS、外部数据可信边界是否处理。
5. 性能
   - 是否有 N+1、无界查询、同步阻塞或热路径大对象。
   - UI 是否有不必要重渲染。
   - 列表接口是否分页。

## 流程

1. 先理解意图：任务、规格、预期行为。
2. 先看测试：是否测行为、边界和回归。
3. 再看实现：按五轴逐文件审查。
4. 给发现分级：阻塞问题放前面，建议放后面。
5. 核验证证据：测试、build、手工验证、截图或请求证据。

## 发现格式

 findings 优先，按严重程度排序：

```markdown
- [Critical] `path/file.ts:42`：会导致数据丢失。原因... 修复建议...
- [Important] `path/file.ts:88`：边界值未处理。原因... 修复建议...
- [Suggestion] `path/file.ts:120`：可以简化命名或结构。
```

没有问题时也要说明剩余风险或未验证项。

## 大小与依赖

- 约 100 行变更：容易审。
- 约 300 行变更：可接受，前提是单一逻辑变更。
- 约 1000 行变更：要求拆分，除非是可机械验证的删除或重命名。

新增依赖前确认：现有栈能否解决、体积、维护状态、漏洞和 license。

## 红旗

- 只说 “LGTM” 没有证据。
- 只看测试是否通过，不看行为和风险。
- 大 PR 无法审清仍批准。
- bugfix 没有回归测试。
- 安全敏感变更没有安全视角。
- 接受“以后再清理”。

## 验证

审查完成前确认：

- [ ] Critical 已解决。
- [ ] Important 已解决或有明确延期理由。
- [ ] 测试和 build 证据存在。
- [ ] 变更说明能解释 what 和 why。
