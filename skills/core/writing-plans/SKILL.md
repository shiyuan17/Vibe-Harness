# 编写实现计划

把已认可的规格转成可交给另一位工程师或 agent 执行的计划。计划必须决策完整：文件、接口、测试、命令和验收标准都写清楚。

开场说明：“我正在使用 writing-plans skill 创建实现计划。”

## 计划要求

- 默认保存到 `docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md`，除非用户指定其他位置。
- 如果规格包含多个独立子系统，先拆成多个计划。
- 每个任务都应有独立可验证的产物。
- 计划中不得出现“待定”“稍后实现”“补充细节”或“写合适测试”这类占位。
- 若步骤需要改代码，写出具体代码或足够精确的接口。
- 使用测试驱动节奏：失败测试、确认失败、最小实现、确认通过、提交。

## 文件结构

写任务前先锁定文件边界：

- 创建或修改哪些文件。
- 每个文件负责什么。
- 文件之间暴露哪些函数、类型、命令或模板。
- 哪些任务依赖前置任务产物。

## 计划头

每份计划以此结构开头：

```markdown
# [功能名称] 实现计划

> **给 agentic workers：** 必需子技能：安装时使用 subagent-driven-development（推荐）或 executing-plans 按任务实现本计划。步骤使用 checkbox（`- [ ]`）跟踪。

**目标：** [一句话说明要构建什么]

**架构：** [2-3 句说明实现方式]

**技术栈：** [关键技术或库]

## 全局约束

[逐条列出规格中的全局约束：版本、依赖、命名、平台、验证命令等。]

---
```

## 任务模板

```markdown
### 任务 N：[组件名称]

**文件：**
- 新建：`exact/path/to/file.py`
- 修改：`exact/path/to/existing.py`
- 测试：`tests/exact/path/to/test.py`

**接口：**
- 消费：[来自前序任务的精确签名或产物]
- 产出：[后续任务依赖的函数、类型、文件或命令]

- [ ] **步骤 1：写失败测试**

[给出测试代码]

- [ ] **步骤 2：运行测试并确认失败**

运行：`[命令]`
预期：失败，因为 `[预期失败原因]`

- [ ] **步骤 3：写最小实现**

[给出实现代码或精确修改]

- [ ] **步骤 4：运行测试并确认通过**

运行：`[命令]`
预期：通过

- [ ] **步骤 5：提交**

运行：`git add ... && git commit -m "..."`
```

## 自审

计划完成后重新检查：

1. 规格覆盖：每个需求都能指向某个任务。
2. 占位扫描：没有模糊词或未定义引用。
3. 类型一致：后续任务使用的名字与前序任务产出的签名一致。
4. 验证完整：每个任务都有命令和预期结果。

## 交接

计划保存后，提供执行选择：

```text
计划已完成并保存到 `docs/superpowers/plans/<filename>.md`。有两种执行方式：

1. Subagent-Driven（推荐）：每个任务派发一个新 subagent，并在任务间审查
2. Inline Execution：在当前 session 中使用 executing-plans 分 checkpoint 执行
```
