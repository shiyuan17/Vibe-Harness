# Subagent 驱动开发

用于 full profile 的高阶执行。目标是在父 Agent 控制下，把真正独立的 child 交给最小上下文执行，并通过单一任务 Markdown 保留可验证状态。

## 使用条件

- 已有决策完整的实现计划。
- 任务之间写入范围清楚，不需要多个 agent 同时改同一文件。
- 单 Agent 已不足以经济地完成，且隔离收益高于派发和 fan-in 成本。
- 父任务和 child 已各自登记一个 v2 `docs/tasks/<任务编号>.md`，任务图校验通过。

## 执行协议

1. 先审计划：发现互相矛盾、缺验收或越权写入时先暂停。
2. 父 Agent 是任务 Markdown 的唯一维护者，按执行批次派发；同批只允许无依赖、无冲突且写入范围不重叠的 child。
3. 子 Agent 只接收 child 文档中的目标、输入、接口、约束、写入范围、不得修改范围、输出格式和验证命令，不读取无关长计划。
4. 子 Agent 不得编辑任务控制文档、创建孙任务、再委派或扩大范围；需要拆分、依赖未满足、越界或无法验证时返回阻塞状态。
5. 子 Agent 固定返回：状态、变更摘要、变更路径、验证证据、未验证项、剩余风险、下一步动作；自报测试和自审不是父 Agent 的完成证据。
6. 父 Agent 核对实际 diff 与证据，把结果持久化回对应任务 Markdown；只有阻断问题解决并复审后才推进后续批次。
7. Fan-in 时由父 Agent 汇总、去重、处理冲突、清理 merge-back、审查最终 diff，并在合并后的目标工作区执行父任务的集成验证。

## 单一真值

每个节点只使用一个任务 Markdown：目标、控制块和 AC 是 brief；状态、验收证据、剩余风险和下一步是执行报告。不要再创建平行的 brief、report、workflow manifest 或 progress ledger；审查包只按完整任务的 Red Team 门禁生成。

## 红旗

- 让子 agent 读取整份长计划，而不是任务 brief。
- 让子 Agent 再委派、创建孙任务或直接修改父任务文档。
- reviewer 只有“LGTM”，没有规格符合性和质量结论。
- 上一批次仍有阻断问题就派发下一批次。
- 压缩或恢复后不查任务 Markdown，重复派发已完成任务。
- 把临时 worktree 的验证当成最终合并位置验证。

## 完成证据

- 父子双向关系、批次、依赖、冲突和写入范围通过任务图校验。
- 每个 child 的固定格式结果已由父 Agent 核对并写回任务 Markdown。
- 阻断审查意见已修复或有明确批准的延期。
- merge-back 无待处理项，最终 diff 获独立审查，集成验证来自合并后的目标工作区。
