# BL-CNAS 验证适配补丁

业务目录保持只读；本目录不是通用核心，也不随包安装。当前交付使用 `validation-delivery-v2.patch`，以本轮读取的真实文件为基准生成；`validation-delivery.patch` 保留为上一版历史产物，不要同时应用两份。当前补丁包含：

- changed 的只读 `--plan`、显式 paths／冻结上下文优先与覆盖缺口报告；未知文件不自动触发前后端全量，明确 full 仍保留完整选择。
- 识别 `.infisical.json` 与模拟器操作脚本的实际静态检查，不读取或打印凭据；不把所有 JSON／脚本一概跳过或归为后端。
- quick 拆为七个实际原子检查，沿用 Harness 逐项缓存；不把大聚合标成 deterministic。后端仍为非确定性，不伪造通过。
- 资源锁在原子阶段选出后获取，前端路径不获取 backend-build；typecheck 仍按包和真实消费方，不宣称文件级类型检查。
- Vue 与四个源码读取型页面契约输入显式映射；启用／关闭按钮使用模板 AST 断言，不按标签字符串切片。
- 删除文件按冻结基线核实；已登记契约输入沿映射验证，无法界定消费者时报告覆盖缺口，不以域内小样本宣称完整覆盖。
- 普通组织模块测试文件直接选择对应测试类，不因新增一个测试文件回退后端全量；公共构建输入仍保留扩大范围。
- 已知 Vitest 配置只扩大实际消费组；Vitest 使用 runner 配置加载与禁用磁盘缓存，避免向共享依赖写入临时配置和测试缓存。
- 后端本地检查显式声明 transaction 证据：同一冻结交付批次的 stage 结果供 publish 消费，不将非确定性结果缓存到其他任务。
- 新增七项 Node 范围回归；不新增 DAG、Issue 或审批台账。

## 应用顺序

1. 先在 Vibe-Harness 完成源码验收，通过受管安装更新业务项目的运行时；不要手工覆盖 `.agents/runtime` 或禁用 Hook。
2. 核对业务项目当前修改归属。先对 `validation-delivery-v2.patch` 执行 `git apply --check <absolute-patch>`，预览冲突；本轮 `git -C <business-root> apply --check <absolute-patch>` 仍被正在运行的旧 Hook 误分类拒绝，尚未在业务项目完成该检查。源包已补精确 `-C` 只读语法及写入负控，但这不表示当前宿主已生效。补丁不应直接覆盖并发变化，冲突时重建补丁。
3. 在已授权的业务实施任务中应用补丁；`vibe-harness.config.json` 的配置迁移也在补丁中。运行中的旧 Hook 拒绝直接编辑隔离配置副本，因此配置只在内存中机械生成文本补丁，没有写入业务或隔离副本的控制面。
4. 先运行 `node --test frontend/scripts/validation-scope-regression.test.mjs`。传感器任务用显式两个 paths 展开 changed 计划，应只选 lint、包 typecheck、相关 test，不出现后端／桥接阶段。再运行页面契约测试及所选原子检查。
5. 对最终真实交付 diff 重新规划，不能只用任务 paths 遮掉新增契约、依赖或远端引入的组合变化。显式 full／CI 要求仍执行完整范围。

## 证据与缺口

隔离副本的七项范围回归已实测通过。没有对业务目录执行写入、业务测试套件、类型检查或远端操作；模板 AST 修改尚需在业务依赖环境执行。已生成补丁不是已部署，也不是业务验收通过。

原始配置和源码没有进入通用规则、Skill 或 manifest。补丁生成器 `build-patch.mjs` 只读业务源，输出必须在业务目录之外，且拒绝覆写已存在产物。重新生成使用新输出文件名，人工核对后选择最终补丁；不要删除或覆写业务工作区来使补丁适配。
